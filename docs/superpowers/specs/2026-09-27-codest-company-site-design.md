# Codest 회사 소개 사이트 설계

작성일: 2026-09-27
상태: 구현 중. 아래 초기 설계 이후 사용자가 크몽 회사 소개 화면을 새 레퍼런스로 지정했으며, 현재 구현에는 이 최신 요청을 우선 적용한다.

## 최신 디자인 변경 (2026-09-27)

- [크몽 회사 소개](https://www.kmongcorp.com/)의 흰 헤더, 넓은 여백, 좌측 정렬의 큰 한글 제목과 밝고 어두운 섹션의 리듬을 참고한다. 레이아웃·문구·이미지를 그대로 복제하지 않는다.
- 초기의 전체 다크 화면을 흰 배경 중심으로 바꾸고, 네이비 첫 화면과 Codest 로고의 블루·시안만 강조색으로 사용한다.
- 딱딱한 기업 소개 문장보다 방문자가 제작하려는 서비스에 관해 편하게 이야기할 수 있는 한국어 문장으로 바꾼다. 확인되지 않은 실적 수치는 쓰지 않는다.
- 제공된 로고 외의 이미지 영역은 비워 둔다. 포트폴리오는 큰 빈 이미지 자리와 제목·설명을 조합한다.
- 문의 페이지에서는 실제 입력 항목을 항상 보여주되 운영 설정이 완성되기 전에는 비활성 미리보기와 이메일 링크를 표시한다.

## 1. 목적과 확정된 요구사항

웹·앱 외주개발을 의뢰하려는 방문자가 Codest의 작업 사례와 제공 서비스를 이해하고 제작문의를 남길 수 있는 한국어 회사 소개 사이트를 만든다.

사용자가 선택한 방향:

- Linear처럼 차분한 다크 화면에 Work & Co처럼 작업 사례를 크게 보여주는 구성.
- 첨부된 Codest 로고의 블루·시안 색상 사용.
- 제공된 로고를 제외한 신규 페이지의 이미지 영역은 빈칸으로 두고 사용자가 나중에 채운다.
- 랜딩, 포트폴리오 목록·상세, 제작문의 페이지 구현.
- 모든 페이지를 모바일·태블릿·데스크톱에 대응하는 반응형으로 구현하고 기존 `/driver`, `/privacy`도 작은 화면의 가로 넘침을 확인한다.
- 포트폴리오는 GitHub의 Markdown 파일을 Next 서버에서 가져와 정적으로 렌더링.
- 제작문의 입력 항목은 이름, 전화번호, 이메일, 제작내용.
- 제작문의 폼에 Cloudflare Turnstile을 적용하고 서버에서 검증한 뒤 접수한다.
- 문의는 Supabase의 `inquiries`에 저장하고, 이메일 큐와 발송 이력은 범용 테이블 `notification`에서 관리.
- `notification`에는 문의 전용 ID나 외래 키를 두지 않는다. 문의 외의 이벤트도 같은 구조로 알림을 생성할 수 있어야 한다.
- 문의 접수 확인 메일은 접수 요청에서 직접 발송하지 않고 별도 배치가 접수자의 이메일로 발송한다. `from`, `replyTo`, `bcc`는 모두 `kdh@codest.kr`로 설정하여 담당자도 같은 메일을 숨은 참조로 받는다. 별도의 관리자용 메일은 중복 생성하지 않는다. 다른 유형의 알림은 해당 알림에 지정된 주소를 사용한다.
- 이메일 발송은 Nodemailer와 SMTP2GO를 사용한다. 기존 Dooray는 `codest.kr` 수신 메일 서비스로 유지한다.
- 메일은 코드에 둔 Handlebars HTML 템플릿으로 작성한다. 알림의 `type`으로 템플릿을 선택하고 `payload`의 치환 값으로 제목·HTML·일반 텍스트를 만든다.
- 디자인은 선택한 실제 레퍼런스를 기준으로 검토한다. 반복 카드, 과한 그라데이션과 발광 장식으로 화면을 채우는 구성을 피한다.
- 기존 Next.js 14.1 프로젝트를 최신 안정 버전으로 업데이트.

아래의 구체적인 레이아웃, GitHub 갱신 주기와 배치 주기는 승인된 설계의 기본값으로 사용한다.

## 2. 화면과 브랜드

### 공통 스타일

- 배경: 거의 검은 네이비 `#080C12`, 구분 영역 `#111923`.
- 본문: 밝은 회백색 `#F4F7FA`, 보조 설명 `#A4AFBD`.
- 강조: `#20C0FF`, 보조 시안 `#30D0FF`. 로고의 불투명한 파란 픽셀을 샘플링한 근사값이며 공식 브랜드 가이드 값은 아니다.
- 주요 파란 버튼에는 어두운 글자를 사용하고 실제 대비를 검증한다.
- 넓은 여백과 큰 한글 제목을 사용한다. 본문과 프로젝트 설명은 읽기 쉬운 크기와 줄 간격으로 제한한다.
- 작은 카드가 반복되는 구성보다 넓은 프로젝트 이미지, 제목, 짧은 설명을 사용한다.
- 데스크톱 콘텐츠 폭은 약 1200px, 모바일은 한 열로 구성한다.
- 헤더는 흰색 워드마크와 포트폴리오·제작문의 메뉴를 표시한다. 제공된 로고는 브랜드 표시에 사용하며, 첫 화면의 별도 비주얼 영역과 작업 이미지는 비워 둔다.
- 제공된 두 PNG는 투명 배경을 포함한다. 원본 비율과 형태를 보존한다. 표시할 때 파일 안의 넓은 투명 여백을 고려한다.
- 이미지가 없는 영역에는 정해진 비율의 빈 배경만 표시한다. 대체 사진·생성 이미지·기존 작업 이미지를 임의로 채우거나 깨진 이미지 아이콘을 표시하지 않는다.
- 모션은 짧은 등장 및 호버 효과 위주로 사용하고, 모션 감소 설정을 존중한다.

### 레퍼런스 적용 기준

2026-09-27 Linear 첫 화면과 Work & Co의 첫 화면·고객 목록을 브라우저에서 다시 확인했다. 아래는 관찰을 Codest에 적용하는 설계 판단이다.

| 기준 | Codest에 적용할 내용 |
| --- | --- |
| Linear: 짙은 단색 배경, 왼쪽 정렬의 큰 제목, 절제된 보조 문구, 얇은 경계 | 한글 제목의 줄바꿈과 읽는 순서를 먼저 잡고, 배경색·글자 크기·여백으로 위계를 만든다. |
| Work & Co: 큰 제목과 작업 영역, 넓은 여백, 간결한 사례 설명·링크 | 프로젝트를 이미지 영역→제목→짧은 설명 순으로 보여주고 카드 외곽 장식을 최소화한다. |
| Codest 로고: 블루·시안과 흰색 워드마크 | 파란색은 주요 버튼·링크·작은 강조점에 집중한다. 로고 외의 그림은 추가하지 않는다. |

- 첫 화면은 왼쪽 정렬의 제목·짧은 설명·CTA와 넓은 빈 비주얼 영역으로 구성한다. 장식용 영문 배지나 떠다니는 통계 패널을 넣지 않는다.
- 서비스와 진행 과정은 텍스트·번호·얇은 구분선으로 정리한다. 모든 섹션을 동일한 둥근 카드 3개로 반복하지 않는다.
- 배경의 빛 번짐, 오로라·그라데이션 구체, 유리 패널, 장식용 격자·입자, 그라데이션 제목은 사용하지 않는다. 제공된 로고 자체의 입체 표현은 보존한다.
- 프로젝트 이미지는 실제 자료가 들어올 자리로 남긴다. 빈칸을 아이콘·그라데이션·가상 대시보드로 메우지 않는다.
- 구현 후 레퍼런스와 실제 화면을 나란히 확인해 제목 정렬, 글자 위계, 작업 영역 비중, 여백, 색의 사용량을 검토한다. 일반적인 레이아웃 자동 검사만으로 디자인 검토를 대신하지 않는다.

### 랜딩 `/`

1. 첫 화면: 핵심 문구, 웹·앱 개발 소개, `제작 문의하기`와 `포트폴리오 보기` 버튼, 사용자가 채울 빈 비주얼 영역.
2. 대표 작업: 넓은 이미지 영역과 설명으로 최대 3개 프로젝트 소개. 이미지 영역은 초기에는 비워 둔다.
3. 제공 서비스: 웹 서비스, 모바일 앱, 운영·관리 시스템 개발.
4. 진행 과정: 상담 → 범위·일정 협의 → 디자인·개발 → 검수·출시.
5. 문의 유도와 공통 푸터.

카피 초안은 “아이디어를, 실제로 쓰이는 서비스로.”이다. 확인되지 않은 고객 수, 매출 성과, 경력, 수상 실적, 고객 로고를 만들어 넣지 않는다.

### 포트폴리오 `/portfolio`, `/portfolio/[slug]`

- 목록: 프로젝트 대표 이미지 영역, 제목, 한 줄 소개, 분야·기술 표시. 데스크톱은 두 열, 모바일은 한 열. 대표 이미지 미설정 시 16:10 비율의 빈 영역을 유지한다.
- 상세: 제목과 요약 → 대표 이미지 영역 → 개요·담당 범위·구현 내용 Markdown 본문 → 제작문의 링크. 초기 대표 이미지 영역은 비워 둔다.
- 프로젝트가 적은 초기에는 검색·필터를 추가하지 않는다.
- 기존 `/driver`의 설명을 바탕으로 스쿨버스 서비스 사례 하나를 구성할 수 있다. 기존 이미지를 새 포트폴리오에 자동으로 가져오지 않으며, 자료에 없는 담당 범위나 성과는 추정하지 않는다.

### 제작문의 `/contact`

- 이름·전화번호·이메일·제작내용을 필수 입력으로 받는다.
- 입력 제한: 이름 80자, 전화번호 30자, 이메일 254자, 제작내용 20~5000자.
- 전화번호는 공백·괄호·하이픈·국가번호 표기를 허용하고 숫자 개수를 검증한다.
- 개인정보 수집 목적·항목 안내와 동의 체크를 제공한다.
- Cloudflare Turnstile Managed 위젯을 제출 버튼 앞에 둔다. 공식 스크립트로 렌더링하고 `action=inquiry`를 사용한다. 작은 화면에서도 넘치지 않도록 flexible 크기와 좁은 화면의 compact 크기를 적용하며 위젯을 잘라내거나 숨기지 않는다.
- 인증 완료 토큰이 있어야 전송할 수 있다. 로딩·실패·만료 시 상태와 재시도 방법을 안내하고 이름·연락처·제작내용은 유지한다. 토큰은 5분 유효·1회 사용이므로 재전송 시 새 토큰을 얻되 기존 `submission_id`는 유지한다.
- 전송 중에는 버튼을 잠그고, 오류가 나면 작성한 내용을 보존한다.
- 문의와 발송 대기 건이 DB에 함께 저장되면 즉시 접수 성공을 안내한다. 메일 발송은 배치가 처리하며 방문자는 발송을 기다리지 않는다.
- 예산, 파일 첨부, 회원가입은 초기 범위에 포함하지 않는다.

## 3. Next.js 업데이트와 기존 페이지

2026-09-27 공식 npm 레지스트리에서 확인한 안정 버전인 Next.js 16.3.6과 React/React DOM 19.3.0을 기준으로 업데이트한다. 실제 설치 시 지원되는 안정 패치와 의존성 호환성을 다시 확인하고 잠금 파일에 고정한다.

- App Router와 TypeScript 구조를 유지한다.
- React 타입, eslint-config-next 등 연동되는 의존성을 함께 조정한다.
- 제거된 `next lint`를 ESLint CLI와 Flat Config로 교체하고 lint를 build와 별도로 실행한다.
- Node 24 환경에서 검증한다. 배포 환경에도 지원되는 Node 버전을 명시한다.
- Tailwind 3은 유지한다. 프레임워크 업데이트에 필요하지 않은 CSS 도구 교체는 하지 않는다.
- 기존 `/driver` URL과 내용은 유지한다. 마케팅 페이지의 다크 스타일은 범위를 제한하여 기존 서비스 소개가 깨지지 않도록 한다.
- `/privacy`에 있는 기존 앱·위치 정보 관련 내용을 임의 삭제하거나 홈페이지 문의 정책으로 덮어쓰지 않는다. 문의용 고지와 기존 앱 고지를 구분해 표시한다.

## 4. GitHub Markdown 콘텐츠 흐름

`GitHub Markdown → 서버 전용 콘텐츠 로더 → 메타데이터 검증 → 목록·상세 정적 렌더링`

- 저장소, 브랜치, 디렉터리는 서버 환경변수로 지정한다. 권장 디렉터리는 `content/portfolio`이다.
- 이 저장소 또는 별도 콘텐츠 저장소를 사용할 수 있다. 기본 동작은 지정한 하나의 저장소만 읽는다.
- 공개 저장소는 공개 접근을 사용하고, 비공개 저장소는 읽기 전용 GitHub 토큰을 서버에서만 사용한다.
- 각 프로젝트는 파일명에 해당하는 slug를 가진 `.md` 파일 하나로 작성한다.
- Front matter: `title`, `summary`, `cover`, `category`, `stack`, `publishedAt`, `featured`, `draft`.
- `cover`는 생략 또는 `null`을 허용한다. 초기 예제에도 이미지 URL을 채우지 않는다. 사용자가 나중에 `cover`나 본문의 Markdown 이미지 경로를 추가하면 렌더링하며, 이미지 부재가 빌드·페이지 오류를 일으키지 않도록 한다.
- 본문은 기존 react-markdown/remark-gfm 구성을 활용한다. 임의 HTML·스크립트·MDX 실행은 허용하지 않는다.
- 이미지 경로는 승인된 GitHub 저장소의 기준 경로 또는 검증된 HTTPS URL로 해석한다.
- 목록과 상세 페이지는 명시적인 캐시 정책과 10분 재검증 주기를 사용한다. 갱신 시점 이후의 요청으로 새 콘텐츠를 반영하며 정확히 10분 뒤 즉시 게시되는 예약 동작은 아니다.
- 새 slug도 배포 없이 생성될 수 있도록 동적 경로 생성을 지원한다.
- GitHub 갱신 실패 시 기존 정상 캐시를 유지한다. 유효한 캐시가 없을 때는 일시적인 불러오기 실패를 알리며 정상적인 빈 목록으로 숨기지 않는다.
- 공개된 slug가 없는 경우 404를 반환하고, 초안은 목록·직접 상세 접근 모두에서 제외한다.
- 각 상세 페이지의 제목·설명과 sitemap을 콘텐츠에 맞춰 생성한다. 공유 이미지는 사용자가 제공한 유효한 이미지가 있을 때만 지정한다.

실제 GitHub 저장소 주소는 연결 설정으로 제공받는다. 설정 전에는 명시적인 로컬 개발 모드에서만 예제 Markdown을 사용할 수 있으며, 운영 환경이 조용히 예제 콘텐츠로 대체되지 않도록 한다.

## 5. 문의 저장과 알림 배치

접수: `폼 제출 → Next 입력 검증·Turnstile 서버 검증 → inquiries와 notification을 한 트랜잭션으로 저장 → 접수 완료`

발송: `스케줄러 → 배치 실행 → notification의 대기 건 확보 → type에 해당하는 템플릿에 payload 치환 → 접수자에게 발송하고 담당자를 숨은 참조 → 결과 기록`

### 문의 테이블 `inquiries`

문의 내용과 업무 처리 상태만 저장한다.

- `id`, `submission_id`(고유), `created_at`
- `name`, `phone`, `email`, `message`
- `consent_version`, `consented_at`
- `status`: `new`, `contacted`, `closed`

### 범용 알림 테이블 `notification`

알림 한 건을 한 행으로 저장한다. 수신 대상 `to`는 이메일이나 전화번호를 담을 수 있는 독립된 TEXT 컬럼으로 유지하고, 이메일의 발신·회신·숨은 참조 설정은 사용자가 제안한 `recipt` JSONB 컬럼 하나에 묶는다. 기존 `subject`, `body`는 템플릿에서 생성하므로 `type`, `payload`로 대체하여 8개 컬럼을 유지한다.

| 컬럼 | 타입 | 용도 |
| --- | --- | --- |
| `id` | UUID, PK | 알림 식별자 |
| `to` | TEXT | 수신 대상 한 개. 현재 이메일, 추후 전화번호도 사용 |
| `recipt` | JSONB, nullable | 이메일 발신·회신·숨은 참조 설정 |
| `type` | TEXT | 등록된 템플릿 식별자. 예: `inquiry_received.v1` |
| `payload` | JSONB | 템플릿의 치환 값. 완성된 HTML이나 템플릿 소스는 저장하지 않음 |
| `status` | TEXT | `pending`, `processing`, `sent`, `failed`, `needs_review` |
| `created_at` | TIMESTAMPTZ | 생성 시각 |
| `sent_at` | TIMESTAMPTZ, nullable | SMTP 접수 성공 시각 |

`to`에는 접수자의 이메일을 저장하며, `recipt`에는 다음 구조의 이메일 설정만 저장한다. `replyTo`, `bcc`는 복수 주소를 담는 배열이다. 현재 서비스에서는 발신자를 하나로 제한하고 `from`은 표시 이름과 주소를 가진 객체로 둔다.

```json
{
  "from": { "name": "Codest", "address": "kdh@codest.kr" },
  "replyTo": ["kdh@codest.kr"],
  "bcc": ["kdh@codest.kr"]
}
```

`to`는 필수이며 JSON 안에 중복 저장하지 않는다. DB의 `to` 컬럼 자체에 이메일 전용 제약은 두지 않는다. 현재 이메일 등록·발송 경로에서는 `to`의 단일 이메일 형식과 `recipt.from.address`를 필수로 검증한다. `from.name`은 선택이고 `replyTo`, `bcc`는 생략 또는 빈 배열을 허용한다. 배열 원소는 각각 이메일 주소 하나인 문자열이며 쉼표로 이어 붙인 주소 목록이나 헤더 개행은 허용하지 않는다. 등록 시와 발송 전에 같은 스키마로 검증하고, 허용된 주소 필드만 Nodemailer에 전달한다. 임의 JSON 전체를 메일 옵션으로 펼치지 않는다.

전화번호를 수신 대상으로 사용하는 문자 발송은 추후 연동 범위다. 이를 위해 `to`는 범용 문자열, `recipt`는 nullable로 두지만 현재 배치가 전화번호를 SMTP 수신 주소로 넘기지는 않는다. 이메일 형식이나 설정이 유효하지 않은 대기 건은 발송 없이 `failed`로 기록한다.

범용성은 어떤 업무든 수신 대상·주소 설정·템플릿 식별자·치환 값을 넣어 같은 알림 등록 함수를 사용할 수 있다는 의미로 제한한다. `type`은 템플릿 선택용이다. 별도 채널·메타데이터·완성된 발송 본문 사본·응답 코드·오류 상세·재시도 횟수·잠금 정보·시도별 로그 컬럼은 추가하지 않는다. 현재 구현하는 발송 채널은 이메일이며 행 자체가 해당 알림의 발송 기록이다. 장애 조사는 알림 ID를 포함한 정제된 서버 로그와 SMTP2GO 발송 이력으로 수행한다.

문의 전용 식별자나 문의 테이블 외래 키를 두지 않는다. 배치는 알림 행과 코드에 등록된 템플릿만으로 발송하며 문의 테이블을 조회하지 않는다. 호출자는 `type`과 해당 템플릿에 필요한 `payload`만 전달한다. 발송을 시작한 알림의 주소·type·payload는 변경하지 않는다.

### HTML 메일 템플릿

- 저장소에 Handlebars HTML 템플릿과 타입별 payload 검증 스키마를 둔다. `inquiry_received.v1`은 문의 접수 확인, `notice.v1`은 문의와 무관한 일반 알림이다.
- 문의 payload는 `name`, `phone`, `email`, `message`, `receiptId` 문자열로 구성한다. `receiptId`는 표시용 치환 값이며 관계 키로 사용하지 않는다. 일반 알림 payload는 `title`, `message` 문자열로 구성한다.
- 배치는 등록된 템플릿만 선택한다. 임의 파일 경로나 사용자가 입력한 템플릿 코드를 실행하지 않는다. 알 수 없는 type이나 필수 payload 누락은 SMTP 호출 없이 `failed`로 처리한다.
- Handlebars의 기본 `{{value}}` HTML 이스케이프를 유지하고 사용자 입력에 triple braces·SafeString·noEscape를 사용하지 않는다. 문의 내용의 줄바꿈은 서버에서 줄 배열로 나누고 각 줄을 이스케이프하여 표시한다. payload에 들어 있는 `{{...}}`는 다시 템플릿으로 실행하지 않는다.
- 렌더러는 `{subject, html, text}`를 반환한다. HTML은 Nodemailer의 `html`, 일반 텍스트 대체 본문은 `text`로 전달한다. 제목과 텍스트 대체 본문에는 HTML 엔티티가 노출되지 않게 별도로 생성하고 제목의 개행을 거부한다.
- 메일은 600px 안쪽의 읽기 쉬운 한 열 구조, 표 기반 배치와 인라인 CSS를 사용한다. Codest 이름·파란 강조선·접수 안내·제출 내용·회신 안내를 배치하며 이미지가 없어도 내용을 읽을 수 있게 한다. Gmail·Outlook·Dooray와 모바일에서 줄바꿈과 긴 문의 내용을 확인한다.
- 이미 큐에 들어간 알림의 템플릿·payload 계약은 유지한다. 호환되지 않는 변경은 새 type 버전으로 추가하고 이전 버전 템플릿도 보존한다. 별도 버전 컬럼은 두지 않는다.

### 접수의 일관성

- 문의 접수용 서버 DB 함수가 문의 한 건과 접수 확인 알림 한 건을 한 트랜잭션에서 저장한다. 독립된 `to` 컬럼에는 형식을 검증한 접수자 이메일 한 개를 저장하고 서버가 `recipt`를 구성한다. `recipt.from.address`는 `kdh@codest.kr`, `recipt.from.name`은 `Codest`, `recipt.replyTo`와 `recipt.bcc`는 각각 `["kdh@codest.kr"]`로 지정한다. 문의와 알림 중 하나만 저장되는 상태를 허용하지 않는다.
- 같은 제출의 네트워크 재시도는 `submission_id`로 구분한다. 새 Turnstile 토큰 검증 후 같은 문의 내용이면 기존 접수 결과를 반환하고, 다른 내용이면 충돌로 처리한다. 토큰은 저장하거나 내용 비교에 포함하지 않는다.
- 새 문의가 실제로 생성된 경우에만 알림을 등록한다. 기존 `submission_id`의 재요청은 알림을 추가 생성하지 않는다. 다른 내부 기능은 문의를 만들지 않고 범용 알림 등록 함수만 호출할 수 있다.
- DB 저장 실패 시 성공 안내를 하지 않는다. 저장이 완료되면 메일 발송 결과와 무관하게 접수 완료를 안내한다.
- 메일 서비스의 일시적인 장애는 문의 접수를 막지 않는다. 문의와 알림은 보존하고 발송 실패는 대시보드에서 확인할 수 있게 한다.

### 배치 실행과 실패 처리

- Supabase Cron이 5분마다 Next 서버의 `POST /api/internal/notifications`를 호출한다.
- 실행 인증용 비밀값을 서버 환경변수와 Supabase Vault에 저장하고 요청 헤더로 전달한다. 인증 실패 시 DB 조회나 발송을 실행하지 않는다.
- 한 번에 최대 10건을 처리하며 알림 레코드 한 건당 `to`와 선택적인 `recipt.bcc`를 지정해 메일 한 통을 발송한다. 문의 접수 확인은 접수자와 담당자가 같은 본문을 받는다. 처리 대상은 `pending` 상태뿐이다.
- DB에서 `FOR UPDATE SKIP LOCKED`로 행을 확보하고 같은 트랜잭션에서 `processing`으로 바꾼다. 동시 배치가 같은 알림을 가져가지 못하게 한다. 별도의 잠금 컬럼을 추가하지 않는다.
- SMTP 요청과 배치 실행에 시간 한도를 둔다. 실행 한도 안에서 시작할 수 없는 남은 건은 `pending`으로 두고 다음 배치가 처리한다.
- Nodemailer의 `sendMail()`이 성공하고 `to`와 `recipt.bcc`의 중복을 제거한 모든 대상이 `accepted`에 포함되면 `sent`와 `sent_at`을 기록한다. `from`과 `replyTo`는 수신 대상 계산에 넣지 않는다. 전체 대상의 SMTP 미접수가 확인되면 `failed`, 일부 대상만 접수되면 `needs_review`로 남긴다. 일부 접수된 메일을 전체 재발송하지 않는다. 진단용 오류는 서버 로그에 알림 ID와 정제한 원인만 남기고, DB에 수신자별 결과·응답 코드·상세 오류를 저장하지 않는다.
- 접수 결과가 불명확한 연결 종료·타임아웃은 `needs_review`로 남긴다. SMTP 접수 후 DB 기록 실패나 서버 중단으로 `processing`에 남은 건도 자동 회수·재발송하지 않고 운영자가 발송 이력을 확인한다.
- 초기에는 자동 재시도와 단계별 재시도 간격을 구현하지 않는다. 운영자가 실패 건을 확인하고 원인을 해결한 뒤 필요하면 같은 type·payload로 새 알림을 등록한다. 일부 대상만 실패한 경우에는 SMTP2GO 이력을 확인해 실패한 주소에만 새 알림을 보내고 이미 접수된 주소를 다시 포함하지 않는다. 원래 행은 이력으로 남기며 상태를 `pending`으로 되돌리지 않는다.
- 재발송 전에는 이전 배치가 종료되었고 재발송 대상에 대해 SMTP가 메일을 접수하지 않았음을 확인한다. 추적용 Message-ID는 알림 ID에서 계산하여 메일 헤더에 사용하고 별도 컬럼으로 저장하지 않는다. SMTP에서 동일 Message-ID를 중복 제거한다고 가정하지 않는다.
- Supabase 대시보드에서 문의 처리 상태와 알림 실패·검토 대상을 각각 확인한다. 별도 관리자 페이지는 만들지 않는다.

### 이메일 내용과 운영 연결

- Next 배치 엔드포인트를 Node.js 런타임으로 실행하고 Nodemailer SMTP transport로 SMTP2GO에 연결한다. 알림 레코드의 독립된 `to` 컬럼을 메일의 `to`로 전달하고, `recipt`에서 검증한 `from`, `replyTo`, `bcc`를 각각 같은 이름의 메일 옵션으로 전달한다. `type`, `payload`로 렌더링한 `subject`, `html`, `text`를 전달한다. 숨은 참조는 Nodemailer의 `bcc` 옵션으로 지정하고 본문이나 공개 수신 헤더에 복사하지 않는다.
- `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`, `MAIL_FROM`을 서버 환경변수로 받는다. 기본값은 호스트 `mail.smtp2go.com`, 포트 `587`, `SMTP_SECURE=false`와 STARTTLS 필수이다. 계정 정보는 SMTP2GO의 SMTP Users에서 발급한 인증정보를 사용한다.
- 465 포트는 즉시 TLS, 587 포트는 STARTTLS와 `requireTLS`를 사용하며 인증서 검증을 끄지 않는다. SMTP 연결·응답 타임아웃은 배치 실행 한도보다 짧게 지정한다.
- SMTP2GO에서 `codest.kr`을 Sender Domain으로 인증하고 `MAIL_FROM=kdh@codest.kr`을 사용한다. 문의 알림 등록 시 `recipt.from.address`, `recipt.replyTo`, `recipt.bcc`에 이 주소를 앞서 정의한 객체·배열 구조로 저장하며 화면에 보이는 발신 이름은 `Codest`로 표시한다. 접수자는 자신이 제출한 이메일로 확인 메일을 받고 담당자는 기존 Dooray의 `kdh@codest.kr`에서 숨은 참조 사본을 받는다. 배치는 발송 시점의 기본값으로 저장된 주소를 덮어쓰지 않는다.
- Dooray 수신용 MX 레코드를 유지한다. SMTP2GO 계정 화면에 표시되는 도메인 인증용 CNAME을 추가하며, 계정별 DNS 값은 임의로 만들지 않는다. 도메인 인증은 발신 권한 설정이며 별도의 수신 메일함 생성으로 간주하지 않는다.
- 배포 서버의 SMTP 연결 가능 여부와 SMTP2GO 계정의 발송 한도를 확인한다. `verify()`로 연결·인증을 점검하고 실제 발신 주소의 발송 권한, 접수자 주소와 Dooray의 숨은 참조 수신, 접수자 답장의 Dooray 도착은 시험 메일로 별도 확인한다. 연결 검증이 실제 메일 수신 검증을 대체하지 않는다.
- 문의 접수 확인 템플릿의 제목은 `[Codest] 제작문의가 접수되었습니다`로 하고, HTML과 일반 텍스트 본문은 접수 안내와 “내용을 확인한 뒤 연락드리겠습니다.”라는 문구, 제출한 이름·전화번호·이메일·제작내용, 접수 식별자를 표시한다. 내부 전용 메모는 포함하지 않는다. 접수자가 메일에 답장하면 `replyTo`에 지정한 `kdh@codest.kr`로 전달된다. 담당자가 숨은 참조 사본을 보고 접수자에게 연락할 때는 `to`나 본문에 표시된 접수자 주소를 수신자로 지정한다. 접수 식별자는 표시용 payload 값이며 관계 키가 아니다. 다른 유형의 알림은 등록된 템플릿에 맞는 payload를 사용한다.
- `sent`는 SMTP 서버의 접수 성공을 의미하며 받은편지함 도착을 보장한다는 문구를 사용하지 않는다.
- 두 테이블 모두 RLS를 켜고 공개 역할의 조회·쓰기 권한을 열지 않는다. DB 함수도 서버 역할에만 실행 권한을 부여한다. 비밀 키와 문의 내용을 브라우저 코드 또는 공개 로그에 포함하지 않는다.
- 범용 알림 생성은 인증된 내부 기능에만 허용한다. 공개 문의 폼이 제공하는 이메일은 접수 확인의 단일 수신 주소로만 사용하고, 별도 수신 목록·발신·회신·숨은 참조 주소나 type·템플릿 소스는 클라이언트가 지정할 수 없다. 서버가 입력 필드로 허용된 payload를 구성한다.
- DB 마이그레이션, 배치 스케줄 등록·해제 방법과 실패 건의 재처리 방법을 저장소에 제공한다. 스케줄러 호출 성공과 실제 발송 건수·결과를 구분해서 확인한다.
- 운영 최초 활성화 전에 DB·메일·스케줄러 연결을 점검한다. 연결이 준비되기 전에는 폼 대신 이메일 연락처를 안내한다. 활성화 이후 메일 서비스의 일시적인 장애 중에도 문의는 저장한다.

## 6. 입력 보호와 운영 설정

- 서버에서 Cloudflare Siteverify를 호출하여 토큰의 `success`, 허용된 `hostname`, `action=inquiry`를 확인한 후에만 문의를 저장한다. 토큰 누락·위조·만료·재사용·호스트나 action 불일치 시 저장하지 않는다. 외부 검증 장애도 검증을 우회하지 않고 재시도 안내로 처리한다.
- `NEXT_PUBLIC_TURNSTILE_SITE_KEY`는 공개 위젯 키, `TURNSTILE_SECRET_KEY`는 서버 전용 비밀 키, `TURNSTILE_ALLOWED_HOSTNAMES`는 정확한 허용 호스트 목록이다. 토큰이나 비밀 키를 DB·로그에 저장하지 않는다. Turnstile은 요청 빈도 제한·서버 입력 검증과 함께 사용한다.
- 로컬·자동 테스트에는 Cloudflare 공식 테스트 키와 격리된 검증 모의를 사용한다. 운영에서 검증을 건너뛰는 플래그나 테스트 키를 허용하지 않는다. 스크립트 차단·네트워크 실패 시 문의 내용을 유지하고 `kdh@codest.kr` 연락 방법도 표시한다.
- 서버 입력 검증, 요청 크기 제한, 숨김 스팸 필드, 중복 제출 방지를 적용한다.
- 공개 문의 API에는 요청 빈도 제한을 적용한다. 여러 서버 인스턴스에서도 유효하도록 Supabase의 원자적 제한 카운터를 이용하고, 제한 자료는 문의 내용과 분리한다.
- IP 식별이 필요한 경우 배포 환경에서 신뢰할 수 있는 주소 정보만 사용하고, 원문 IP 대신 서버 비밀값으로 해시한 값을 짧게 보관한다. 배포 프록시 설정을 확인하지 않은 임의 헤더를 신뢰하지 않는다.
- 메일 내용과 전화번호·이메일을 일반 애플리케이션 로그에 기록하지 않는다.
- 문의 개인정보 고지에는 실제 수집 항목·이용 목적·보유 기간·위탁 정보를 반영한다. 보유 기간 등 운영 정책은 운영자가 제공해야 하며 기존 앱의 고지를 그대로 재사용하거나 임의로 사실처럼 작성하지 않는다.

서비스 연결 단계에서 필요한 값은 GitHub 저장소 설정, Supabase 프로젝트 URL과 서버 비밀 키, Turnstile 사이트 키·비밀 키·허용 호스트, 도메인 인증을 마친 SMTP2GO 계정의 SMTP 인증정보, 사이트의 운영 URL, 배치 실행 인증값과 스케줄 설정, 문의 개인정보 운영 정책이다. 비밀정보는 Git에 넣지 않고 환경변수 또는 Supabase Vault로 주입한다. 이 값의 제공은 설계 선택과 별개의 운영 연결 조건이다.

## 7. 검증과 완료 기준

- Next.js 업데이트 후 lint, TypeScript 검사, production build가 통과한다.
- 모바일 390px, 태블릿 768px, 데스크톱 1440px에서 랜딩·목록·상세·문의의 시각적 배치와 가로 넘침을 확인한다. 320px의 좁은 화면과 기존 `/driver`, `/privacy`의 가로 넘침도 확인한다.
- 키보드 탐색, 입력 레이블, 오류 안내, 포커스, 색 대비, 모션 감소를 점검한다.
- 콘텐츠 검증은 front matter 오류, 초안 숨김, 새 slug, 잘못된 slug, 이미지 없는 콘텐츠, 사용자가 추가한 상대 이미지 경로, GitHub 실패 시 캐시 유지에 집중한다. 빈 이미지 영역의 비율 유지와 대체 사진이 자동으로 채워지지 않는 동작도 확인한다.
- 문의 검증은 유효한 제출, 잘못된 입력, 중복 요청, 두 테이블의 원자적 저장·롤백, 접수 요청에서 메일을 발송하지 않는 동작, 빈도 제한에 집중한다.
- Turnstile 검증은 성공·실패·만료·중복 토큰·호스트/action 불일치·Siteverify 장애, 실패 시 DB 호출 차단, 새 토큰과 같은 submission_id로 재시도할 때 중복 접수가 없는지 확인한다. 위젯의 스크립트 차단과 모바일 크기도 확인한다.
- 템플릿 검증은 type별 선택, 필수 payload 누락, 알 수 없는 type, HTML 삽입·중괄호 문자열·한글·여러 줄의 안전한 출력, 제목/HTML/text 생성, 배포 결과물의 `.hbs` 포함과 이메일 화면을 확인한다.
- 배치 검증은 인증 실패, 동시 실행에서 한 건을 한 작업자만 확보하는지, 주 수신자와 숨은 참조 모두의 SMTP 접수 확인, 일부 접수와 전체 실패·결과 불명확 상태의 구분, 서버 중단 후 `processing` 건 자동 재발송 차단, 수동 재발송 시 원래 행의 이력 보존과 이미 접수된 대상의 제외에 집중한다. 접수 한 건에 알림 한 행만 생성되는지와 `from`, `replyTo`, `bcc` 매핑, 수신 메일의 Bcc 헤더 제거도 확인한다.
- 문의 레코드 없이 일반 공지 메일을 생성·발송할 수 있는지, 복수 회신 주소·숨은 참조와 숨은 참조 없는 알림도 동일한 배치에서 처리되는지, 배치가 문의 테이블을 조회하지 않는지 검증한다. 독립된 `to` 컬럼과 `recipt`의 필수 필드·배열·각 주소 검증, 전화번호 대상의 SMTP 호출 차단, 임의 메일 옵션 전달 차단, 문의 외래 키 부재와 공개 폼의 복수 주소·헤더 개행·발신 및 숨은 참조 주소 변조 차단도 확인한다.
- 기존 `/driver`, `/privacy`가 유지되는지 확인한다.
- 레퍼런스와 나란히 보며 제목 정렬·위계, 여백, 포트폴리오 비중, 파란색 사용량을 검토하고 금지한 장식·반복 카드 구성이 들어가지 않았는지 확인한다.
- 자격증명 없이 수행한 테스트는 모의 연동 검증으로 구분한다. 실제 Supabase 저장, 스케줄러의 배치 호출과 실제 메일 수신은 서비스 연결 후 별도로 확인해야 한다.
- README와 `.env.example`, DB 마이그레이션, 포트폴리오 작성 예제, 배치 운영·재처리 방법을 제공한다.
