# Codest 회사 소개 사이트 설계

작성일: 2026-09-27
상태: 구현 전 사용자 검토용

## 1. 목적과 확정된 요구사항

웹·앱 외주개발을 의뢰하려는 방문자가 Codest의 작업 사례와 제공 서비스를 이해하고 제작문의를 남길 수 있는 한국어 회사 소개 사이트를 만든다.

사용자가 선택한 방향:

- Linear처럼 차분한 다크 화면에 Work & Co처럼 작업 사례를 크게 보여주는 구성.
- 첨부된 Codest 로고의 블루·시안 색상 사용.
- 랜딩, 포트폴리오 목록·상세, 제작문의 페이지 구현.
- 포트폴리오는 GitHub의 Markdown 파일을 Next 서버에서 가져와 정적으로 렌더링.
- 제작문의 입력 항목은 이름, 전화번호, 이메일, 제작내용.
- 문의는 Supabase의 `inquiries`에 저장하고, 문의별 알림 발송 이력은 `notification_admin`에 분리.
- 메일 알림은 문의 접수 요청에서 직접 발송하지 않고 별도 배치가 kdh@codest.kr로 발송.
- 기존 Next.js 14.1 프로젝트를 최신 안정 버전으로 업데이트.

아래의 구체적인 레이아웃, GitHub 갱신 주기, 메일 발송 수단과 배치 주기는 이번 설계에서 제안하는 기본값이다. 설계 검토 시 함께 확정한다.

## 2. 화면과 브랜드

### 공통 스타일

- 배경: 거의 검은 네이비 `#080C12`, 구분 영역 `#111923`.
- 본문: 밝은 회백색 `#F4F7FA`, 보조 설명 `#A4AFBD`.
- 강조: `#20C0FF`, 보조 시안 `#30D0FF`. 로고의 불투명한 파란 픽셀을 샘플링한 근사값이며 공식 브랜드 가이드 값은 아니다.
- 주요 파란 버튼에는 어두운 글자를 사용하고 실제 대비를 검증한다.
- 넓은 여백과 큰 한글 제목을 사용한다. 본문과 프로젝트 설명은 읽기 쉬운 크기와 줄 간격으로 제한한다.
- 작은 카드가 반복되는 구성보다 넓은 프로젝트 이미지, 제목, 짧은 설명을 사용한다.
- 데스크톱 콘텐츠 폭은 약 1200px, 모바일은 한 열로 구성한다.
- 헤더는 흰색 워드마크와 포트폴리오·제작문의 메뉴를 표시한다. 입체 심볼은 첫 화면의 시각 요소로 사용한다.
- 제공된 두 PNG는 투명 배경을 포함한다. 원본 비율과 형태를 보존한다. 표시할 때 파일 안의 넓은 투명 여백을 고려한다.
- 모션은 짧은 등장 및 호버 효과 위주로 사용하고, 모션 감소 설정을 존중한다.

### 랜딩 `/`

1. 첫 화면: 핵심 문구, 웹·앱 개발 소개, `제작 문의하기`와 `포트폴리오 보기` 버튼, Codest 심볼.
2. 대표 작업: 넓은 이미지 중심으로 최대 3개 프로젝트 소개.
3. 제공 서비스: 웹 서비스, 모바일 앱, 운영·관리 시스템 개발.
4. 진행 과정: 상담 → 범위·일정 협의 → 디자인·개발 → 검수·출시.
5. 문의 유도와 공통 푸터.

카피 초안은 “아이디어를, 실제로 쓰이는 서비스로.”이다. 확인되지 않은 고객 수, 매출 성과, 경력, 수상 실적, 고객 로고를 만들어 넣지 않는다.

### 포트폴리오 `/portfolio`, `/portfolio/[slug]`

- 목록: 프로젝트 대표 이미지, 제목, 한 줄 소개, 분야·기술 표시. 데스크톱은 두 열, 모바일은 한 열.
- 상세: 제목과 요약 → 대표 이미지 → 개요·담당 범위·구현 내용 Markdown 본문 → 제작문의 링크.
- 프로젝트가 적은 초기에는 검색·필터를 추가하지 않는다.
- 기존 `/driver`의 설명과 이미지로 스쿨버스 서비스 사례 하나를 구성할 수 있다. 기존 자료에 없는 담당 범위나 성과는 추정하지 않는다.

### 제작문의 `/contact`

- 이름·전화번호·이메일·제작내용을 필수 입력으로 받는다.
- 입력 제한: 이름 80자, 전화번호 30자, 이메일 254자, 제작내용 20~5000자.
- 전화번호는 공백·괄호·하이픈·국가번호 표기를 허용하고 숫자 개수를 검증한다.
- 개인정보 수집 목적·항목 안내와 동의 체크를 제공한다.
- 전송 중에는 버튼을 잠그고, 오류가 나면 작성한 내용을 보존한다.
- 문의와 발송 대기 건이 DB에 함께 저장되면 즉시 접수 성공을 안내한다. 메일 발송은 배치가 처리하며 방문자는 발송을 기다리지 않는다.
- 예산, 파일 첨부, 회원가입은 초기 범위에 포함하지 않는다.

## 3. Next.js 업데이트와 기존 페이지

2026-09-27 공식 npm 레지스트리에서 확인한 안정 버전인 Next.js 16.3.6과 React/React DOM 19.3.0을 기준으로 업데이트한다. 실제 설치 시 지원되는 안정 패치와 의존성 호환성을 다시 확인하고 잠금 파일에 고정한다.

- App Router와 TypeScript 구조를 유지한다.
- React 타입, eslint-config-next 등 연동되는 의존성을 함께 조정한다.
- 제거된 `next lint`를 ESLint CLI와 Flat Config로 교체하고 lint를 build와 별도로 실행한다.
- Node 24 환경에서 검증한다. 배포 환경에도 지원되는 Node 버전을 명시한다.
- Tailwind 3은 유지한다. 프레임워크 업데이트에 필요하지 않은 CSS 도구 교체는 하지 않는다.
- 기존 `/driver` URL과 내용은 유지한다. 마케팅 페이지의 다크 스타일은 범위를 제한하여 기존 서비스 소개가 깨지지 않도록 한다.
- `/privacy`에 있는 기존 앱·위치 정보 관련 내용을 임의 삭제하거나 홈페이지 문의 정책으로 덮어쓰지 않는다. 문의용 고지와 기존 앱 고지를 구분해 표시한다.

## 4. GitHub Markdown 콘텐츠 흐름

`GitHub Markdown → 서버 전용 콘텐츠 로더 → 메타데이터 검증 → 목록·상세 정적 렌더링`

- 저장소, 브랜치, 디렉터리는 서버 환경변수로 지정한다. 권장 디렉터리는 `content/portfolio`이다.
- 이 저장소 또는 별도 콘텐츠 저장소를 사용할 수 있다. 기본 동작은 지정한 하나의 저장소만 읽는다.
- 공개 저장소는 공개 접근을 사용하고, 비공개 저장소는 읽기 전용 GitHub 토큰을 서버에서만 사용한다.
- 각 프로젝트는 파일명에 해당하는 slug를 가진 `.md` 파일 하나로 작성한다.
- Front matter: `title`, `summary`, `cover`, `category`, `stack`, `publishedAt`, `featured`, `draft`.
- 본문은 기존 react-markdown/remark-gfm 구성을 활용한다. 임의 HTML·스크립트·MDX 실행은 허용하지 않는다.
- 이미지 경로는 승인된 GitHub 저장소의 기준 경로 또는 검증된 HTTPS URL로 해석한다.
- 목록과 상세 페이지는 명시적인 캐시 정책과 10분 재검증 주기를 사용한다. 갱신 시점 이후의 요청으로 새 콘텐츠를 반영하며 정확히 10분 뒤 즉시 게시되는 예약 동작은 아니다.
- 새 slug도 배포 없이 생성될 수 있도록 동적 경로 생성을 지원한다.
- GitHub 갱신 실패 시 기존 정상 캐시를 유지한다. 유효한 캐시가 없을 때는 일시적인 불러오기 실패를 알리며 정상적인 빈 목록으로 숨기지 않는다.
- 공개된 slug가 없는 경우 404를 반환하고, 초안은 목록·직접 상세 접근 모두에서 제외한다.
- 각 상세 페이지의 제목·설명·공유 이미지와 sitemap을 콘텐츠에 맞춰 생성한다.

실제 GitHub 저장소 주소는 연결 설정으로 제공받는다. 설정 전에는 명시적인 로컬 개발 모드에서만 예제 Markdown을 사용할 수 있으며, 운영 환경이 조용히 예제 콘텐츠로 대체되지 않도록 한다.

## 5. 문의 저장과 알림 배치

접수: `폼 제출 → Next 서버 검증 → inquiries와 notification_admin을 한 트랜잭션으로 저장 → 접수 완료`

발송: `스케줄러 → 배치 실행 → 발송 대기 건 확보 → 이메일 발송 → notification_admin에 결과 기록`

### 문의 테이블 `inquiries`

문의 내용과 업무 처리 상태만 저장한다.

- `id`, `submission_id`(고유), `created_at`
- `name`, `phone`, `email`, `message`
- `consent_version`, `consented_at`
- `status`: `new`, `contacted`, `closed`

### 문의별 알림 테이블 `notification_admin`

문의 한 건에 대한 관리자 메일 알림의 대기 상태와 발송 이력을 저장한다. 초기 수신자는 `kdh@codest.kr` 한 명이며 문의당 알림 레코드 하나를 만든다. 재시도는 같은 레코드에 누적한다.

- `id`, `inquiry_id`(문의 외래 키·고유), `created_at`, `updated_at`
- `recipient`: `kdh@codest.kr`
- `status`: `pending`, `processing`, `retry`, `sent`, `failed`, `needs_review`
- `attempt_count`, `next_attempt_at`, `first_attempt_at`, `last_attempt_at`
- `provider_message_id`, `sent_at`, `last_error_code`
- `lock_token`, `locked_until`: 중복 배치 실행을 막기 위한 작업 점유 정보
- `request_payload`: 최초 발송 전에 확정한 이메일 요청 내용. 재시도 시 같은 내용을 사용한다.
- `attempts`(JSONB): 시도 번호, 시작·완료 시각, 결과, 발송 서비스 식별자, 정제한 오류 코드를 누적한다. 원문 오류 응답이나 비밀 키는 넣지 않는다.

`inquiries.id`와 `notification_admin.inquiry_id`로 연결한다. 알림 발송 상태나 시도 횟수를 `inquiries`에 중복 저장하지 않는다.

### 접수의 일관성

- 서버 전용 DB 함수를 통해 문의와 `pending` 알림을 한 트랜잭션으로 생성한다. 둘 중 하나만 저장되는 상태를 허용하지 않는다.
- 같은 제출의 네트워크 재시도는 `submission_id`로 구분한다. 같은 내용이면 기존 접수 결과를 반환하고, 다른 내용이면 충돌로 처리한다.
- DB 저장 실패 시 성공 안내를 하지 않는다. 저장이 완료되면 메일 발송 결과와 무관하게 접수 완료를 안내한다.
- 메일 서비스의 일시적인 장애는 문의 접수를 막지 않는다. 발송 대기 건은 DB에 남아 후속 배치에서 처리한다.

### 배치 실행과 재시도

- 기본 제안은 Supabase Cron이 5분마다 Next 서버의 `POST /api/internal/notifications`를 호출하는 방식이다. 5분은 사용자 확정 전의 제안값이다.
- 실행 인증용 비밀값을 서버 환경변수와 Supabase Vault에 저장하고 요청 헤더로 전달한다. 인증 실패 시 DB 조회나 발송을 실행하지 않는다.
- 한 번에 최대 10건을 처리하며 문의 한 건당 메일 한 통을 발송한다. 조회 대상은 실행 시간이 도래한 `pending`·`retry`와 점유 기간이 만료된 `processing`이다.
- DB에서 작업을 원자적으로 점유하고 잠금 토큰으로 결과 갱신을 검증한다. 동시 배치가 같은 알림을 보내거나 만료된 작업자가 새 작업자의 결과를 덮어쓰지 않도록 한다.
- 각 외부 요청에 타임아웃을 설정하고 배치의 실행 시간 한도를 둔다. 점유 기간은 실행 한도보다 길게 잡으며 남은 건은 다음 실행으로 넘긴다.
- 발송 성공 시 `sent`와 서비스 식별자·시각을 기록한다. 실패 시 시도 이력을 남긴다.
- 일시적인 실패는 `retry`로 전환하고 5분·15분·1시간·3시간 간격으로 재시도한다. 서비스의 `Retry-After`가 더 길면 그 값을 따른다. 최초 시도를 포함해 자동 발송 시도는 최대 5회이다.
- 재시도 횟수를 소진하거나 재시도로 해결되지 않는 요청 오류가 발생하면 `failed`로 남긴다. 조회·점유한 사실만으로 발송 성공으로 간주하지 않는다.
- 발송 서비스의 고정 멱등 키를 알림 ID에서 생성하고 재시도마다 같은 요청 내용을 사용한다. 발송 직후 서버가 중단되어 DB에 성공을 기록하지 못한 경우에도 중복 발송을 줄인다.
- 최초 외부 발송 시도 시각인 `first_attempt_at`으로부터 Resend 멱등 키 보존 기간인 24시간을 넘긴 미완료 건은 `needs_review`로 전환해 자동 발송을 중단한다. 아직 한 번도 발송을 시도하지 않은 대기 건에는 이 제한을 적용하지 않는다. 운영자가 발송 서비스의 이력을 확인한 뒤 재처리하며, 확인 없이 새 멱등 키로 자동 발송하지 않는다.
- Supabase 대시보드에서 문의 처리 상태와 알림 실패·검토 대상을 각각 확인한다. 별도 관리자 페이지는 만들지 않는다.

### 이메일 내용과 운영 연결

- 기본 메일 서비스 제안은 Resend이다. 발신자는 도메인 인증을 마친 Codest 주소를 설정값으로 받는다. 방문자 이메일은 `Reply-To`로 사용한다.
- 이름·전화번호·이메일·제작내용과 접수 식별자를 전달한다. 본문은 안전하게 이스케이프하거나 텍스트 형식으로 생성한다.
- `sent`는 발송 서비스의 접수 성공을 의미하며 받은편지함 도착을 보장한다는 문구를 사용하지 않는다.
- 두 테이블 모두 RLS를 켜고 공개 역할의 조회·쓰기 권한을 열지 않는다. DB 함수도 서버 역할에만 실행 권한을 부여한다. 비밀 키와 문의 내용을 브라우저 코드 또는 공개 로그에 포함하지 않는다.
- DB 마이그레이션, 배치 스케줄 등록·해제 방법과 실패 건의 재처리 방법을 저장소에 제공한다. 스케줄러 호출 성공과 실제 발송 건수·결과를 구분해서 확인한다.
- 운영 최초 활성화 전에 DB·메일·스케줄러 연결을 점검한다. 연결이 준비되기 전에는 폼 대신 이메일 연락처를 안내한다. 활성화 이후 메일 서비스의 일시적인 장애 중에도 문의는 저장한다.

## 6. 입력 보호와 운영 설정

- 서버 입력 검증, 요청 크기 제한, 숨김 스팸 필드, 중복 제출 방지를 적용한다.
- 공개 문의 API에는 요청 빈도 제한을 적용한다. 여러 서버 인스턴스에서도 유효하도록 Supabase의 원자적 제한 카운터를 이용하고, 제한 자료는 문의 내용과 분리한다.
- IP 식별이 필요한 경우 배포 환경에서 신뢰할 수 있는 주소 정보만 사용하고, 원문 IP 대신 서버 비밀값으로 해시한 값을 짧게 보관한다. 배포 프록시 설정을 확인하지 않은 임의 헤더를 신뢰하지 않는다.
- 메일 내용과 전화번호·이메일을 일반 애플리케이션 로그에 기록하지 않는다.
- 문의 개인정보 고지에는 실제 수집 항목·이용 목적·보유 기간·위탁 정보를 반영한다. 보유 기간 등 운영 정책은 운영자가 제공해야 하며 기존 앱의 고지를 그대로 재사용하거나 임의로 사실처럼 작성하지 않는다.

서비스 연결 단계에서 필요한 값은 GitHub 저장소 설정, Supabase 프로젝트 URL과 서버 비밀 키, 인증된 메일 발신 주소와 Resend 키, 사이트의 운영 URL, 배치 실행 인증값과 스케줄 설정, 문의 개인정보 운영 정책이다. 비밀정보는 Git에 넣지 않고 환경변수 또는 Supabase Vault로 주입한다. 이 값의 제공은 설계 선택과 별개의 운영 연결 조건이다.

## 7. 검증과 완료 기준

- Next.js 업데이트 후 lint, TypeScript 검사, production build가 통과한다.
- 모바일 390px와 데스크톱 1440px에서 랜딩·목록·상세·문의의 시각적 배치와 가로 넘침을 확인한다.
- 키보드 탐색, 입력 레이블, 오류 안내, 포커스, 색 대비, 모션 감소를 점검한다.
- 콘텐츠 검증은 front matter 오류, 초안 숨김, 새 slug, 잘못된 slug, 상대 이미지 경로, GitHub 실패 시 캐시 유지에 집중한다.
- 문의 검증은 유효한 제출, 잘못된 입력, 중복 요청, 두 테이블의 원자적 저장·롤백, 접수 요청에서 메일을 발송하지 않는 동작, 빈도 제한에 집중한다.
- 배치 검증은 인증 실패, 동시 실행, 작업 점유 만료, 일시 실패 재시도, 최대 시도 초과, 발송 직후 중단, 멱등 키 만료 후 검토 전환, 요청 내용의 재사용, 시도별 이력 보존에 집중한다.
- 기존 `/driver`, `/privacy`가 유지되는지 확인한다.
- 자격증명 없이 수행한 테스트는 모의 연동 검증으로 구분한다. 실제 Supabase 저장, 스케줄러의 배치 호출과 실제 메일 수신은 서비스 연결 후 별도로 확인해야 한다.
- README와 `.env.example`, DB 마이그레이션, 포트폴리오 작성 예제, 배치 운영·재처리 방법을 제공한다.
